- `ended` display with no end date (issue #136, 2026-10-30): (a) `2021–present` when `status` is `in-development`, the start year alone otherwise; (b) always the start year alone (today's look); (c) `2021–present` for every entry without `ended` (wrong for one-off art and finished releases). ## Known issues

Recorded, not specified; investigation belongs in a separate bug issue.

- **2026-10-30 — `LocalImageUsedWrongly` on draft pages in dev**: after saving in Keystatic while production builds ran in parallel, the dev server threw `LocalImageUsedWrongly` on draft pages; restarting the dev server fixed it. **Resolved (issue #77)**. Cause: `astro build` always rewrites `.astro/content-assets.mjs`, shared with the dev server; the build's draft filter (`withoutDrafts`, `src/content.config.ts`) leaves draft image imports out of it, so a running dev server reloads the map and draft covers stay strings. `.astro/data-store.json` is not shared; saving any content entry or restarting dev heals it. Fix: `npm run build` runs `scripts/build.mjs`, which keeps `.astro/content-assets.mjs` in memory, runs `astro build` and restores the file when the build ends (success, failure or Ctrl+C; not if the process is killed), exiting with the build's code; no-op when the file does not exist (CI). Draft filtering is unchanged. Trade-off: while a build runs, draft pages on a running dev server can still 500 and recover when it ends; a work entry saved during a build gets the pre-build map back until the next content save or dev restart.

## Decided

### 2026-10-30 — Dev-only in-page editor for work entries (issue #136)

- **Decision**: (1) A dev-only editor edits `work` entries in place on `/work/<slug>`: phase 1 title, What I did, description (raw Markdown), Draft, Featured; phase 2 the meta line (kind, context, status, team, started) and a cover thumbnail linking to Keystatic; phase 3 a new optional `ended` date; lists later. Keystatic stays for everything else. (2) It exists only under `astro dev`: a local integration registered only in dev (`injectScript` for a plain-TS client, `astro:server:setup` middleware for a JSON endpoint `<base>__editor/work/<id>`), dev-only `data-editor-*` hooks in the page, and a build test asserting `dist/` holds no editor trace. (3) Saves go through one `PUT` with an allow-list, a content hash for conflict detection, `workSchema` validation of the whole merged entry, loopback/Host/Origin/Content-Type checks, path confinement to top-level `src/content/work/*.md`, temp-file-then-rename writes; never creates, renames or deletes files. (4) Files are written with `js-yaml` `dump` with no options, the call Keystatic makes, keeping the file's key order, dates as plain `YYYY-MM-DD`. (5) The `work` Zod schema moves to `src/lib/work-schema.ts` (`workSchema(image)`) so the collection and the editor share one rule set; field help moves to `FIELD_HELP` in `src/vocab.ts`, shared by Keystatic descriptions and editor tooltips. (6) Description is a plain textarea of Markdown, not `contenteditable`. (7) Explicit save (button, `Ctrl`/`Cmd`+`S`), not autosave.
- **Reason**: the user finds Keystatic's one-column form with help under every label exhausting for small edits. Editing on the page shows the result where it lives. Registering the integration only in dev keeps the static build untouched without relying on runtime flags. Reusing Keystatic's own YAML call keeps both tools able to open each other's saves. A textarea round-trips Markdown byte for byte; `contenteditable` would need an HTML→Markdown converter (a new dependency) and would rewrite Markdoc it does not understand. Explicit save because every write reloads the dev page; autosave would reload mid-typing.
- **Trade-offs**: a second editing path to maintain alongside Keystatic. The first editor save of an import-script file normalises its formatting (as a Keystatic save would). The description has no live preview: the rendered result appears after Save. An unsaved edit is lost if the dev server reloads the page for another reason (code change), beyond the `beforeunload` prompt. The editor writes files from the browser through a local endpoint, a new attack surface on the dev machine, limited by the request checks; `security-auditor` reviews it before merge.
- **Rejected**: an Astro API route or adapter (would put server code in the site and need `output` changes); editing through Keystatic's own API (undocumented, version-bound); the `yaml` library (formats differently from Keystatic); a React island (React is loaded in dev only for Keystatic; plain DOM is enough and keeps the client small); a WYSIWYG description.
- **Migration**: none. No data format change in phases 1–2; `ended` (phase 3) is optional, no version bump; Keystatic gets the field in the same change.
- **Affects**: [section 1](1-stack.md) Admin panel row, new "Dev-only page editor", "Tests"; [section 2](2-content-model.md) "Adding work", new "End date (`ended`)"; [section 3](3-pages.md) route list, "Work page layout", new "Edit mode (dev server only)"; [section 5](5-phases.md) new Phase 6; Open (two items added).

### 2026-10-30 — Work page side column for gallery and posts (issue #119)

- **Decision**: on `/work/<slug>` at ≥ 64rem, when the entry has a gallery or at least one published post, the text sits in a left 2/3 column (What I did, description, Links, Fork, Credits, Tools, Related) and the gallery, then "Posts about this project", in a right 1/3 column (`minmax(0, 2fr) minmax(0, 1fr)`). Header, work embed/cover and the back link stay full width. The side column is not sticky. In it the gallery shows two 4:3 thumbnails per row (a single image spans the column). With neither gallery nor posts the page stays one column as before. Below 64rem the page is one column in today's order. The document order is unchanged, so visual and reading order match at every width. CSS-only; the `:target` lightbox is unchanged and nothing between the page and the lightbox may create a containing block for fixed elements or a stacking context.
- **Reason**: the user found the right half of wide work pages empty, with the text squeezed into the left column. 64rem rather than the blog's 48rem: at 48rem a 1/3 column is about 15rem, too narrow for two thumbnails; a 2/3 text column still holds the 48rem measure at the 80rem page width. Not sticky: a long gallery would need its own scroll area, and `position: sticky` creates a stacking context that would trap the lightbox (`z-index: 10`) under the sticky site header (`z-index: 5`).
- **Trade-offs**: between 48rem and 64rem (tablets, small laptops) work pages stay one column. On wide screens the gallery is no longer seen before the text is reached in the document order. Keyboard focus visits the gallery before the text, as today, although it now sits to the right. Pages without gallery or posts (most published entries today, the reported page included) do not change; see Open.
- **Rejected**: CSS `order` or `display: contents` to place the columns (visual order would differ from reading order; `display: contents` has had accessibility bugs); a sticky side column (see Reason); a 1/4–3/4 split like the blog (thumbnails too small); moving the lightbox overlays out of the gallery markup (not needed while the column is not sticky).
- **Migration**: none. No data format change, no version bump.
- **Affects**: [section 3](3-pages.md) `/work/<slug>` item and new "Work page layout".
- **Amendment (user decision 2026-10-30, option (b) of the former Open item "Work pages with no gallery and no posts")**: the side column becomes the project sheet and applies to every work page that has one. Supersedes, in the Decision above, the left/right contents, the "only with gallery or posts" condition and "the document order is unchanged".
  - **Decision**: the page body is two blocks in document order: the narrative (What I did, description, Fork), then the project sheet (Links, Tools, Credits, Related, gallery, "Posts about this project"). At ≥ 64rem the narrative wrapper is grid column 1 (2/3) and the sheet wrapper column 2 (1/3), one row, same grid and gap as before. With an empty sheet the page stays one 48rem column. Below 64rem: one column, work → What I did → description → Fork → Links → Tools → Credits → Related → gallery → posts. Related goes in the sheet (it is derived from `usedIn`, not prose; on phones it keeps its place after Tools). Fork stays in the narrative, right after the description, so the fork attribution is read with the text it qualifies ([section 6](6-content-rules.md)). Not sticky; lightbox constraints unchanged.
  - **Reason**: the reported page (`/work/ragassembler2d/`) and most published entries have neither gallery nor posts, so the first version left them unchanged; the user chose (b) over (a) keeping them as is and (c) centering the single column. Wrapping each block and placing the wrappers keeps visual, keyboard and reading order identical, which the earlier interleaved placement (gallery first in the DOM, shown on the right) did not fully do.
  - **Trade-offs**: on phones and below 64rem the gallery moves from right after the work to near the end, after Related, so visitors on phones see screenshots later; Links (play/download/source) also come after the description and Fork instead of right after the description. On a page with a long description and a short sheet the right column ends early, leaving space under it. A page whose narrative is empty (no contribution, empty body, not a fork) but has a sheet shows an empty left column; no published entry is in that case today (to be checked by the builder).
  - **Rejected**: CSS `order`, `display: contents` or per-section grid placement to keep the old phone order (visual order would differ from document order); keeping Related in the narrative (on phones it would land before Links, between Fork and the sheet).
  - **Migration**: none. No data format change, no version bump.
  - **Affects**: [section 3](3-pages.md) `/work/<slug>` item and "Work page layout"; Open list (item removed).

### 2026-10-30 — Automated test suite: `npm test` and a PR test workflow (issue #78)

- **Decision**: `npm test` runs Node's built-in test runner serially over `test/*.test.mjs`: build smokes (production and staging exit 0; staging `dist/` HTML has every root-absolute `href`/`src` under `/dev/`), a dev smoke (every page incl. drafts answers 200, then the issue #77 regression after a build; skipped when `CI` is set), and script tests (`exclude-drafts`, `dedupe-media` in a temporary git repo; `check-urls` helpers without network). `scripts/check-urls.mjs` exports its pure helpers behind an entry-point guard. A new workflow `test.yml` runs `npm ci && npm test` on PRs to `dev` and `main` (Node 22, `contents: read`, cancel in progress). `npm test` is the local verify step.
- **Reason**: catch broken builds, base-path leaks, dev-server regressions like #77 and script regressions before merge, at no cost and without a new dependency.
- **Trade-offs**: a full local run takes about 42 s (about 17 s with `CI` set), and it overwrites `dist/` (ending on the production build). Serial runs are slower but avoid the build and dev smokes racing on `dist/` and `.astro/`. The dev smoke cannot run in CI (no drafts), so the #77 regression is only checked locally. The base-path test reads only double-quoted HTML attributes.
- **Rejected**: a test framework dependency (Vitest, Playwright): the built-in runner is enough for smokes; running the tests inside `pages.yml` (a failing test would block a deploy already merged, and the deploy builds both branches).
- **Migration**: none; no data format change.
- **Affects**: [section 1](1-stack.md) workflow build step wording, "Remote URL check" (exported helpers), new "Tests"; [section 3](3-pages.md) base-path "Check".

### 2026-10-29 — Site appearance in the Profile panel; appearance URLs hotlinked; weekly remote URL check

- **Decision**: (1) The `profile` singleton gains an optional group `appearance` with `photo`, `logo`, `favicon`, `banner`, `background` (plus `background.darken` 0–100 %, default 70, and `background.blur` 0–40 px, default 12, applied only when a background image is set). Each image field holds `file` (upload, stored in `src/assets/site/<field>/`, processed by `astro:assets`) or `url`; **`file` wins when both are set**. Every empty field renders today's look; no default background or banner ships. When a background or banner is shown, the page uses the dark palette in both colour schemes. (2) **Explicit, user-approved exception to "no hotlinked media" (AGENTS.md hard rule 6, [section 7](7-lessons.md)), limited to the appearance fields**: a `url` is emitted as-is (`<img src>`, `<link href>`, CSS `url()`), never downloaded, never passed to `astro:assets`, never fetched at build time. The build validates syntax only (`https:`, no quote/paren/backslash/angle/whitespace characters); an unreachable URL never breaks the build. (3) A separate workflow (`remote-urls.yml`, weekly + manual + push to `dev` on content changes) requests appearance URLs and the external URLs in published frontmatter and keeps one issue, "Broken remote URLs", open while any is broken, closing it when all pass. It never blocks the Pages deploy. Permissions `contents: read`, `issues: write`, `GITHUB_TOKEN` only. (4) Work slug `site` reserved; `site/` is not a slug folder.
- **Reason**: the user wants to try looks from the panel without risk, including images that live elsewhere. Hotlinking accepts that an image may vanish (the v2 background was lost that way); the site then degrades to today's look instead of failing, and the weekly report makes it visible. Upload-wins makes "pin a copy" a one-step override.
- **Known risk**: an external URL can expire, change content or be swapped for something else by its host without any commit here; the visitor's browser requests it (IP and referrer go to that host). Fallbacks per field: background/banner show today's look, photo an empty slot, logo the browser's alt text, favicon the browser default. Not an image or a 404 is only caught by the weekly check.
- **Rejected**: snapshotting URLs into the repo by script on commit/sync (user chose direct use); allowing `astro:assets` remote domains (build-time fetch, a build that fails when the host is down); CI checks that fail the deploy (a third-party outage would block publishing); a third-party link-check service.
- **Amends**: AGENTS.md hard rule 6 needs the matching exception (AGENTS.md is edited by the lead). The "CI stays read-only" stance of "Exact-duplicate media resolver" stays true for content: the new workflow writes only issues, never commits or pushes.
- **Migration**: none. All fields optional; existing `profile.json` stays valid; no version bump.
- **Affects**: [section 2](2-content-model.md) "Profile", new "Site appearance", "Drafts stay out of git" (slug folders); [section 3](3-pages.md) every-page and `/` items, reserved slugs, base-path rule; [section 4](4-media.md) "Where local media lives"; [section 1](1-stack.md) Images row and new "Remote URL check"; [section 7](7-lessons.md).

### 2026-10-29 — Exact-duplicate media resolver: fix in the hook, check in CI

- **Decision**: byte-identical files (SHA-256, any type) under `src/assets/` and `public/media/` are merged by `scripts/dedupe-media.mjs`: one copy kept in `src/assets/shared/` or `public/media/shared/` as `<16 hex of SHA-256>.<ext>`, every reference in `src/` and `keystatic.config.*` rewritten in the same path form, other copies deleted. Merges stay within one tree (cross-tree identical files: warning only). Runs in fix mode from the pre-commit hook (re-stages the result; aborts if a file to rewrite has unstaged changes), as a check in the Pages workflow before each Astro build, and by hand (`npm run dupes`, `npm run dupes -- --fix`). The kept copy obeys the per-file draft rule. Defines `public/media/<slug>/` for files served as-is and `public/webgl/<slug>/` (outside the resolver) for WebGL builds.
- **Reason**: duplicates never reach the repo, local drafts are covered too (CI cannot see them), and CI stays read-only.
- **Rejected**: CI auto-fix committing back (needs a write token and bot commits on a repo where only the lead writes to the remote; would also add commits the lead has not reviewed, and CI cannot see local drafts anyway); perceptual matching (false merges); merging across `src/assets/` and `public/` (import vs URL serving are not interchangeable); hash-only names without the extension (breaks MIME detection and Astro's image pipeline).
- **Affects**: [section 2](2-content-model.md) "Drafts stay out of git" (hook) and new "Duplicate media files"; [section 1](1-stack.md) workflow build step; [section 4](4-media.md) "Where local media lives".

Until the v3 cutover, `main` holds a static maintenance page (`index.html`, `404.html`, a self-unregistering `service-worker.js`, `.nojekyll`) and the deploy workflow publishes it as-is. Build detection per checkout: root `package.json` with `astro` → Astro build at the root (output `dist/`); else root `index.html` → static files published as-is; else the run fails. Staging is only ever Astro. v2 is never built.
- **Reason**: v2 is no longer worth keeping deployable; a maintenance page is honest and needs no build.
- **Rejected**: keeping v2 built for the root until cutover (the previous rule).
- **Amends**: "Branches, environments and deploys" below (its build-detection and "`main` keeps publishing v2" parts). Retires the AGENTS.md rule "v2 stays intact and deployable until v3 renders equivalent content" (AGENTS.md is edited by the lead).
- **Affects**: [section 1](1-stack.md) "Repository layout", "Production before cutover", workflow build detection; [section 5](5-phases.md) Phase 1.

### 2026-10-29 — Astro project moves to the repository root (issue #17)

- **Decision**: the Astro project moves from `site/` to the repository root (`package.json`, `astro.config.*`, `src/`, `public/`, `scripts/`, output `dist/`); npm scripts run from the root. Every spec path drops the `site/` prefix (e.g. `src/lib/paths.ts`, `scripts/exclude-drafts.mjs`, `src/assets/<slug>/`).
- **Reason**: with v2 gone the subfolder has no purpose; root-level commands are simpler for people and agents.
- **Consequence**: v2 removal must land before or together with the move, because v2's root `package.json`, `src/` and `public/` occupy the same paths. Open issues that cite `site/…` paths need updating.
- **Affects**: [section 1](1-stack.md) "Repository layout" and build detection; [section 2](2-content-model.md) "Adding work" and "Drafts stay out of git"; [section 3](3-pages.md) "Base-path rule" and its check; [section 5](5-phases.md) Phase 1.

### 2026-10-29 — v3 keeps a self-unregistering service worker (issue #17)

- **Decision**: v3 publishes `public/service-worker.js`, a self-unregistering worker (skipWaiting; on activate delete only v2's `workbox-`/`sw-precache-` caches, unregister, reload window clients; no `fetch` handler). It lands at `/service-worker.js` in production and, inert, at `/dev/service-worker.js` in staging. v3 never registers a worker. Kept until a later decision removes it.
- **Reason**: browsers that installed v2's worker keep serving v2's cached shell until the script at that URL removes itself.
- **Rejected**: clearing every Cache Storage entry (other repos share the `gann4life.github.io` origin); dropping the file at cutover (stale v2 workers would survive).
- **Affects**: [section 1](1-stack.md) "Retired v2 service worker"; [section 3](3-pages.md) route list; [section 5](5-phases.md) Phase 1.

### 2026-10-29 — Branches, environments and deploys

- **Decision**: `main` = production at `https://gann4life.github.io/`; `dev` = staging at `https://gann4life.github.io/dev/`. One workflow on push to `main` or `dev` checks out both branches, builds `main` at the root and `dev` with `base: '/dev/'` (via `DEPLOY_TARGET=staging`), combines both into one artifact and deploys with the official Pages actions; Pages source switches from the `gh-pages` branch to "GitHub Actions". Each checkout is built as Astro if `site/package.json` exists, else as v2 CRA, so `main` keeps publishing v2 until cutover. Staging pages are `noindex, nofollow`, and the staging build has no sitemap or robots.txt. Issue branches start from `dev`, PR into `dev`; a release is a PR `dev` → `main`. `astro-rewrite` becomes `dev`; the 2023 remote `dev` is kept as the tag `archive/dev-2023`. *(Amended 2026-10-29, issue #17: v2 is never built; `main` publishes a static maintenance page until cutover; Astro lives at the repository root; see "v2 retired" and "Astro project moves to the repository root" above.)*
- **Reason**: a staging URL to check work before it goes live, free, no secrets, while v2 stays the production site until v3 is ready.
- **Rejected**: a second staging repo deployed with a personal access token (adds a secret and a second repo to keep in sync); a separate Pages site per branch (impossible: GitHub Pages serves one site per repo); `Disallow: /dev/` in robots.txt (it stops crawlers from seeing `noindex`, so blocked URLs can still be indexed from links).
- **Consequence**: every internal link and asset URL must work under any base path; the new base-path rule makes `withBase` mandatory.
- **Affects**: [section 1](1-stack.md) hosting row and "Branches, environments and deploys"; [section 3](3-pages.md) reserved `/dev/` and "Base-path rule"; [section 5](5-phases.md) Phase 1.

### 2026-10-29 — Unreferenced asset folders are reported, not excluded

- **Decision**: (a) an asset folder that no entry or file references is no longer excluded and is not blocked by the pre-commit hook: the exclude script prints a `WARNING` naming it and exits 0. Folders referenced only by drafts are still excluded. (b) The script reads frontmatter by parsing only the `draft:` and `slug:` lines inside the leading `---` block; no YAML library or other new dependency. *(Amended 2026-10-29: (a) now applies per file, see "Blog follow-ups from issue #14 decided".)*
- **Reason**: (a) excluding unreferenced folders could silently keep legitimate assets out of git (e.g. files referenced in a way the scanner does not see); a warning is enough to find leftovers. (b) Two plain scalar keys written by Keystatic do not justify a dependency.
- **Rejected**: (b) adding a YAML/frontmatter library.
- **Amends**: the "Draft entries never enter git" decision below (its last sentence on unreferenced folders).
- **Affects**: [section 2](2-content-model.md) "Drafts stay out of git": exclude script, frontmatter parsing, asset folder rule.

### 2026-10-29 — Draft entries never enter git

- **Decision**: `draft: true` entries (`work` and `blog`) and their asset folders stay local until published. A Node script in `site/scripts/` writes them into a marked block of `.git/info/exclude`; it runs on `predev`, `prebuild` and from a committed pre-commit hook (`.githooks/pre-commit`, `core.hooksPath`) that blocks staging draft files. Publishing = `draft: false`, after which entry and assets are committed together. Asset folders are excluded unless a non-draft file references them; unreferenced folders are excluded and reported. *(Amended 2026-10-29, issue #11: unreferenced folders are only reported, not excluded. Issue #17: the script now lives in `scripts/` at the repository root. Later 2026-10-29: exclusion is per asset file, not per folder; see "Blog follow-ups from issue #14 decided".)*
- **Reason**: the repo is public and the only thing to keep private is unpublished work. Drafts must not reach the public history, not only the built site.
- **Rejected**: a separate drafts folder (breaks the single Keystatic collection path); a second, private source repo (user rejected it for now).
- **Kept**: the build-time draft filter stays as a second guard for local builds.
- **Not part of the spec** (lead tasks): `git rm --cached` of the 12 draft entries already tracked on the unpushed `astro-rewrite`, and history cleanup before the first push.
- **Affects**: [section 2](2-content-model.md) "Drafts stay out of git" and the `draft` field; [section 1](1-stack.md) admin notes.
