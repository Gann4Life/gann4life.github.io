# 3. Pages

Full-width, image-first site. On thumbnails the text only appears on hover/focus (always shown on touch screens, which cannot hover); elements cascade in on load; pages cross-fade (CSS view transitions, no JS).

- Every page: the header shows the profile `logo` if set, else the name as text; `<link rel="icon">` uses the profile `favicon` if set, else `withBase('/favicon.svg')`; the profile `background`, if set, is a fixed, blurred, darkened layer behind the whole page. Fields and fallbacks: [section 2](2-content-model.md) "Site appearance".
- `/` — hero: name (with the profile `photo` beside it, if set), headline (profile `tagline`), bio and profile links beside the demo reel (profile `reel`); the profile `banner` image, if set, sits full-bleed behind this hero, starting at the top of the page behind the header and fading out downwards ([section 2](2-content-model.md) "Banner drawing"). Then, in this order (user decision 2026-10-30), each section omitted when empty:
  1. **Featured** (4:3 thumbnails) — first section after the hero.
  2. **Latest** (4:3 thumbnails).
  3. **Tools** — each tool is a link to its tool page `withBase('/work/t/<tool-slug>/')`.
  4. **Blog** (user decision 2026-10-30, issue #111) — a feed, not tiles or list rows: the first 3 posts in home order ([section 2](2-content-model.md) "Post order"), each rendered in full, top to bottom, exactly as the blog reader renders a post on `/blog/` ("Blog split view"): date (plus "Draft" on the dev server), title as a link to `withBase('/blog/<slug>/')`, summary if set, cover if set (decorative, `alt=""`), the full body, and "Related work" if any. Headings: the section title "Blog" is an `h2`, each post title an `h3`, "Related work" an `h4`. Each post is an `article`; posts are separated by a horizontal rule only (no box, background or shadow). A pinned post is highlighted (user decision 2026-10-30): a 3px `--accent-2` bar along its left edge and the "Pinned" marker after the date. No "Featured" marker. After the last post, a button-styled link "All posts →" to `withBase('/blog/')` (the existing `.button` class). The section, button included, is omitted when the build includes no post.
  The home has no category bands: the former **Work** / **Hobbies** button bands are removed (user decision 2026-10-30). Categories are reached from the header nav, which lists every category with included work.
- `/work/c/<category>/` — every work in the category as 4:3 thumbnails with the text over the image. Music releases instead get a compact player each, playable in place.
- `/work/t/<tool-slug>/` (and `/work/t/<tool-slug>/<n>/` for page n ≥ 2) — every included work entry whose `tools` contains that tool, as the same 4:3 tile grid and pagination as category pages (24 per page, same `Pager`), same order (featured first, then newest `started`); tiles only, no in-place music players. Header kicker `<name> / Tools`, title = the tool name as written, count line "1 project" / "N projects". One page per tool slug ([section 2](2-content-model.md) "Tool pages"); no index page at `/work/t/`. Not in the header nav. In production the sitemap lists the first page of each tool (`/work/t/<tool-slug>/`), like category pages; staging has no sitemap.
- `/work/all/` (and `/work/all/<n>/` for page n ≥ 2) — every included work entry, same tile grid, order and pagination as tool pages; kicker `<name> / Work`, title "All work", count line "N projects". Linked from a "View all →" button under the home "Latest" band (user decision 2026-10-30, issue #130). Not in the header nav.
- `/work/<slug>` — one page per entry: the work first (embed, or cover image), then the narrative — what I did, description, fork block — then the project sheet — links, tools (each a link to its tool page), credits, related, the gallery, and last "Posts about this project": published posts whose `work` field includes the entry's slug, in list order ([section 2](2-content-model.md) "Post order"), as title + date links (summary under the title when set); the section is omitted when there are none. That is the document and phone order; on wide screens the project sheet moves to a side column ("Work page layout" below).
- `/blog/`, `/blog/page/<n>/` (n ≥ 2) and `/blog/<slug>/` — posts created in `/keystatic` (Blog) and edited in place on the dev server ("Edit mode" below); fields in [section 2](2-content-model.md) "Blog posts". The header links to the blog once a post is published. Layout below ("Blog split view").
- `/sitemap.xml`, `/robots.txt`, `/404.html`.
- `/service-worker.js` — self-unregistering worker that removes v2's; never registered by v3 ([section 1](1-stack.md) "Retired v2 service worker").
- `/keystatic` — CMS (dev server only, not linked publicly).
- `__editor/<collection>/<id>` under the base — JSON endpoint of the in-site editor, dev server only, not a page and never built ([section 1](1-stack.md) "In-site editor").
- No other top-level paths: other repos publish under this domain (e.g. `/RagAssembler2D/`), so v3 must not create routes that shadow them. The work slugs `c`, `t`, `site`, `all`, `blog` and `shared` are reserved (`t` for tool pages; `all` for the all-work page; `site` because `src/assets/site/` holds the appearance images; `blog` and `shared` because `src/assets/blog/` and `src/assets/shared/` are not slug folders, decision 2026-10-31), and the post slug `page` (blog list pagination). `/dev/` is reserved for the staging build ([section 1](1-stack.md)), so no repo of this account may be named `dev` with Pages enabled.

**Blog split view** (user decision 2026-10-30)

All blog routes render the same two-pane layout, fully static: no new client-side JS.

- **Panes (≥ 48rem)**: left 1/4 a compact post list, right 3/4 the selected post rendered for reading (grid `minmax(0, 1fr) minmax(0, 3fr)` inside the gutters; user decision 2026-10-30, issue #106). The list pane is sticky below the header and scrolls on its own when taller than the viewport.
- **List**: posts in list order ([section 2](2-content-model.md) "Post order"), 20 per page. Each item: title (link to `withBase('/blog/<slug>/')`), date, and markers ("Pinned", "Featured", "Draft" on the dev server). No covers, no summary. The selected post's item is highlighted and carries `aria-current="page"`. When there is more than one page, the `Pager` sits under the list: page 1 is `/blog/`, page n is `/blog/page/<n>/`.
- **Reader**: the selected post exactly as today's post page — date (and "Draft"), title, summary, cover, body, "Related work". The home **Blog** feed renders each post with this same markup (one shared component), differing only in heading levels and the reader's box.
- **Which post is selected**:
  - `/blog/` — list page 1, reader shows the first post of the list order.
  - `/blog/page/<n>/` — list page n, reader shows the first post of that page.
  - `/blog/<slug>/` — that post selected; the list shows the page that contains it, and its pager links lead to `/blog/` and `/blog/page/<n>/`.
- **Headings and metadata**: on `/blog/<slug>/` the post title is the `h1`, and title, description, canonical and Open Graph image are the post's, as today. On `/blog/` and `/blog/page/<n>/` the page `h1` is "Blog", the post title is an `h2` linked to the post's own URL, and title/description/canonical are the blog's (canonical = the page's own URL); no Open Graph image. The list is a `nav` labelled "Posts".
- **Phone (< 48rem)**: one pane at a time, by CSS only. `/blog/` and `/blog/page/<n>/` show the list only (the reader pane is not displayed). `/blog/<slug>/` shows the post only, with a "← All posts" link to `withBase('/blog/')` above it; the list pane is not displayed. On wide screens that back link is hidden (the list is visible).
- **Sitemap** (production): `/blog/` and every `/blog/<slug>/`, as today; `/blog/page/<n>/` is not listed (like later category pages).
- No published post: `/blog/` shows "No posts yet." and no panes; no `/blog/page/` or post routes exist.

**Work page layout** (user request 2026-10-30, issue #119; option (b) user decision 2026-10-30)

`/work/<slug>` is fully static; no new client-side JS (the dev-only edit mode below is never part of a build). The same holds for blog pages.

- **Full width, always**: the header (kicker, meta, title, position, authorship) and the work itself (media embeds, or the cover when there are no media), as today. The "← <category>" back link stays last, full width, after the columns.
- **Two blocks, in this document order**:
  - **Narrative**: What I did (contribution + roles), the description (body), Fork.
  - **Project sheet**: Links, Tools, Credits, Related, the gallery, "Posts about this project". Related belongs to the sheet: it lists facts derived from `usedIn` (the entries this one is used in, and the entries used in this one), not prose.
  Each block keeps the order above; a section with no data is omitted, as today.
- **Columns (≥ 64rem), on every work page whose project sheet has at least one section**: the narrative in a left 2/3 column, the project sheet in a right 1/3 column (grid `minmax(0, 2fr) minmax(0, 1fr)` inside the page width, column gap as the blog split view, `clamp(1.5rem, 3vw, 3rem)`). Each column is one wrapper holding its block; the grid places the narrative wrapper in column 1 and the sheet wrapper in column 2, one row, so the visual order is the document order. Both columns start at the same height, right below the work; the first section of each has no top margin. "Posts about this project" sits directly under the gallery with no empty space between them.
  - The narrative keeps its 48rem text measure.
  - The side column is not sticky: it scrolls with the page.
  - An empty narrative (no contribution, empty body, not a fork) still takes column 1; the sheet stays on the right.
- **Empty project sheet** (no links, tools, credits, related, gallery or posts): no side column and no grid; the page is one column, as before this layout (the text does not widen beyond its 48rem measure).
- **Phone and narrow screens (< 64rem)**: one column in the document order: work, What I did, description, Fork, Links, Tools, Credits, Related, gallery, posts. Compared with the order before this layout, the gallery moves from right after the work to after Related, Fork moves before Links, and Tools before Credits. The visual order never differs from the document order at any width (no CSS `order`, no `display: contents`, no grid placement that reorders), so keyboard and screen-reader order match what is seen.
- **Gallery in the side column**: two thumbnails per row (equal columns, 4:3, cropped, as today); a gallery with a single image shows it across the full column width. Captions stay under their thumbnails. Below 64rem the gallery grid is unchanged (auto-fill, 14rem minimum). The thumbnail `sizes` hint matches the rendered width at each breakpoint (a gallery always sits in the side column at ≥ 64rem, since it makes the sheet non-empty).
- **Sheet sections in the side column**: link buttons and tool tags wrap within the column; credit and related lists keep their bullets and indentation.
- **Lightbox**: unchanged, CSS-only (`:target`), and it must still cover the whole viewport above the sticky site header from the side column. So no element between the page and the lightbox (the layout grid, its column wrappers, the gallery) may establish a containing block for fixed descendants or a stacking context: no `transform`, `filter`, `backdrop-filter`, `perspective`, `contain`, `container-type`, `will-change`, opacity below 1, `position: sticky`/`fixed`, a positioned element with a `z-index`, or the load animation (`rise`), on any of them.

**Edit mode (dev server only)** (issue #136, redesigned 2026-10-30; built, #152 to #156; mechanics in [section 1](1-stack.md) "In-site editor")

On the dev server, a work entry's page (`/work/<slug>`) and a post's page (`/blog/<slug>/`) switch into edit mode: the page itself is the form, so every field is edited where it is shown, and the fields the page does not show are edited in a panel. Production and staging builds are unchanged and contain none of it. The public layout does not change for the editor; the exact look of the controls, the bar and the panel is for `ui-ux-designer` to propose within these rules.

- **One "Edit" per item** (dev only; replaces today's Keystatic links and #139's "Edit here"; `src/components/EditLink.astro` becomes this control):
  - On the item's own page (the work page; the selected post on `/blog/<slug>/`): an "Edit" button that turns edit mode on in place.
  - Everywhere else the item has an Edit control today — work tiles (home Featured / Latest, category, tool and all-work pages), the music players on category pages, posts in the home Blog feed and in the `/blog/` and `/blog/page/<n>/` reader — "Edit" is a link to the item's own page with `?edit` (`withBase('/work/<id>/?edit')`, `withBase('/blog/<id>/?edit')`), which opens it already in edit mode.
  - The home "Edit profile" link keeps opening Keystatic (the Profile is not in the in-site editor) and says so in its label ("Edit profile in Keystatic").
- **Entering and leaving**: Edit, or `?edit` in the URL (the client then removes it with `history.replaceState`). "Done" (or `Esc` when nothing is unsaved) leaves. Edit mode survives the reload after a save (per-tab `sessionStorage`, keyed by `<collection>/<id>`).
- **Edit bar** (top of the item, only in edit mode): save state ("Saved" / "Unsaved changes" / the error); Save; "Edit in Keystatic" (secondary, opens the item in Keystatic in a new tab: for the slug, or as a fallback); Done. The bar may be sticky; it is not an ancestor of the gallery, so the lightbox rule above is unaffected.
- **Hooks**: the page root of the item carries `editHooks.entry(collection, id)`; each element that shows a field carries `editHooks.field(name, …)` ([section 1](1-stack.md)). A post is editable only where it is the page's own item (`/blog/<slug>/`), so `PostArticle` emits hooks only when told it is (an `editable` prop); the home feed and the `/blog/` reader emit none.
  - `work`: meta line spans (`kind`, `context`, the year span `started ended`, `status`, `team`); `h1` (`title`); position (`position`); authorship badge (`authorship`); the embeds (`media`) and, when there are none, the cover image (`cover`); What I did paragraph (`contribution`); roles list (`roles`); `article` (`body`); fork block (`origin upstream`); Links (`links`); Tools (`tools`); Credits (`credits`); Related (`usedIn`); gallery (`gallery`).
  - `blog`: date (`date`); title (`title`); summary (`summary`); cover (`cover`); body (`body`); Related work (`work`).
- **In place**: each hooked element is replaced, in the same spot, by the control for each named field, chosen by type from the registry ([section 1](1-stack.md) table): title an input in the `h1`'s font and size; meta-line enums compact selects with the site's labels; dates date inputs (`ended` clearable); longtext and the body auto-growing textareas (the body is raw Markdown, never `contenteditable`/WYSIWYG; the rendered result appears after Save); tags and refs compact multi-selects; lists repeated groups with add, remove and move up / down; images a thumbnail with Replace and Remove (Add when empty). The gallery shows its items as thumbnails with a caption field each and add, remove and move controls; captions are the images' alt text. The body has "Insert image" (file picker, then alt text).
- **Field panel**: every registry field with no hooked element on the rendered page is edited in a panel right under the edit bar, in registry order (= reading order: [section 1](1-stack.md) "Field registry"), with the same controls. This covers fields the page never shows (`draft`, `featured`, `pinned`; `cover` when media are shown; `origin`/`upstream` and `authorship` when they render nothing) and sections omitted because they are empty (e.g. no credits yet); once saved with a value, such a field shows in place. Booleans sit together on one row; short fields are compact (user rule 2026-10-30).
- **Help**: no help text under the controls. Each control has an accessible name and its `help` from the registry as a tooltip (`title`) and as its accessible description (`aria-describedby` to visually hidden text), so keyboard and screen-reader users get it too.
- **Saving**: explicit, never on every keystroke: Save button or `Ctrl`/`Cmd`+`S` sends every changed field, the body and new images in one `PUT`. Picked images show as local previews until saved. On `200` the page reloads once and comes back in edit mode. On `409` the bar says the file changed elsewhere and offers "Reload" (unsaved edits are lost; nothing was written). On `413`/`415` the bar names the image and the limit. On `422` each issue is shown next to its control (in place or in the panel; a nested path such as `credits.0.name` at that item) and in the bar when it has no control; nothing was written. The honesty rules (ai-built roles and position, fork `upstream` and `credits`) reach the user this way, the same rules as the build. Leaving the page with unsaved changes asks for confirmation (`beforeunload`).
- **Not here**: the slug ("Edit in Keystatic"), creating entries and posts (Keystatic, or `npm run sync` / `npm run add` for work), and the Profile.

**Base-path rule** (links and asset URLs)

The same build runs at `/` (production) and `/dev/` (staging), so no URL may assume the site sits at the domain root.

- Every internal link and every URL to a site file (pages, `public/` files such as `favicon.svg`, `sitemap.xml`, OG images) goes through one helper: `withBase(path)` in `src/lib/paths.ts`. It takes a site-relative path (`/work/x/`, `work/x/` or `/`) and returns it prefixed with `import.meta.env.BASE_URL`, with exactly one `/` between base and path and the trailing slash of `path` preserved. It is the only place in `src/` that reads `BASE_URL`.
- Absolute URLs (canonical, `og:url`, `og:image`, sitemap entries) are built as `new URL(withBase(path), Astro.site)`. A path taken from `Astro.url.pathname` already includes the base and is not passed through `withBase` again.
- Active-link checks compare `Astro.url.pathname` against `withBase(...)`, never against a bare `/…` literal.
- Images imported through `astro:assets` already get the base from Astro and need no helper.
- Markdown bodies in `work` and `blog` contain no root-absolute internal links (`](/…)`); related entries go through the `usedIn` (`work`) / `work` (`blog`) fields.
- External URLs (`https://…`) and protocol-relative URLs are untouched. This includes appearance URLs ([section 2](2-content-model.md) "Site appearance"), emitted as-is; appearance uploads go through `astro:assets` (base added by Astro), and the default favicon through `withBase`.
- **Check** (for `design-auditor`): in `src/**/*.{astro,ts,tsx,js,mjs,md,mdx}`, outside `src/lib/paths.ts`, no match for `(href|src|action|content)=["']/[^/]`, for a JSX/template expression whose string or template literal starts with a single `/` and is used as a URL (e.g. ``href={`/work/``, `href={'/blog/'}`, `new URL('/x', …)`), or for `](/` followed by a non-`/` character in Markdown. Any match is a blocking finding. Also: `npm run build` with `DEPLOY_TARGET=staging` and every `href`/`src` in `dist/` that starts with `/` starts with `/dev/`; `npm test` automates this half for double-quoted `href`/`src` attributes in HTML files ([section 1](1-stack.md) "Tests"), the rest stays a review check.
