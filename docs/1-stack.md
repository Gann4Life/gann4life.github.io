# 1. Stack

| Layer | Choice | Notes |
|---|---|---|
| Framework | **Astro** | Static output, content collections with typed schemas |
| Interactive islands | None by default | Players are plain HTML or framework-agnostic scripts (native `<audio>`/embeds). Spine work is shown as video so rigs are never published. 3D work is shown as screenshots, not an in-browser viewer. Add an island only if a component genuinely needs one |
| Admin panel | **In-site editor** (dev server) + **Keystatic** (local mode) | `npm run dev`. Work entries and blog posts are edited on their own page, every field, images included (see "In-site editor"). Keystatic (`localhost:4321/keystatic`) stays as the alternative: "Edit in Keystatic" inside edit mode, creating entries and posts, slugs, and the Profile. Both write the same Markdown files. Remote editing falls back to `github.dev` |
| Hosting | **GitHub Pages** | Free user site at `gann4life.github.io`, deployed from Actions on push to `main` (production) or `dev` (staging under `/dev/`); see "Branches, environments and deploys" |
| Images | In-repo, `astro:assets` + sharp | WebP/AVIF generated at build; stays inside the ~1 GB published-site budget, no CDN. Only exception: appearance fields given as a URL are hotlinked as-is ([section 2](2-content-model.md) "Site appearance") |
| Video | YouTube / Vimeo / itch.io | Embed only |

**Admin decision notes**
- Keystatic local mode needs no OAuth proxy and no server adapter, so the site stays fully static and free.
- Local mode means no browser editing away from the dev machine; `github.dev` covers that for free.
- Drafts edited in the panel stay local and are never committed; see "Drafts stay out of git" in [section 2](2-content-model.md).
- The CMS is additive: plain Markdown files stay the source of truth, so the CMS can be swapped or removed without touching content.

## Branches, environments and deploys

One repo, one Pages site (GitHub Pages serves a single site per repo), two environments:

| Branch | Environment | URL | Indexed |
|---|---|---|---|
| `main` | production | `https://gann4life.github.io/` | yes |
| `dev` | staging | `https://gann4life.github.io/dev/` | no |

**Branch flow**
- Issue branches `<type>/issue-<n>-<slug>` are cut from `dev` and merged into `dev` by PR (staging deploy).
- A release is a PR `dev` → `main` (production deploy).
- **Hotfix**: an urgent production fix is a branch `hotfix/<slug>` (or `hotfix/issue-<n>-<slug>`) cut from `main`, merged into `main` by PR (production deploy); right after, `main` is merged into `dev` so staging carries the fix and the next release PR does not revert it. Nothing else goes to `main` except release PRs.
- `dev` is the former `astro-rewrite`. The v2-era remote `dev` (2023) is kept as the tag `archive/dev-2023` before being replaced.

**Repository layout**
- The Astro project lives at the repository root: `package.json`, `astro.config.*`, `src/`, `public/`, `scripts/`, output `dist/`. `npm run dev`, `npm run build` and every other npm script run from the root. Spec paths are root-relative (`src/lib/paths.ts`, not `site/src/lib/paths.ts`).
- v2 (Create React App) is retired and its files are not on `dev`. It survives only in git history and the tag `archive/v2`.

**Production before cutover**
- Until the v3 cutover (release PR `dev` → `main` carrying the Astro project), `main` holds only a static maintenance page: `index.html`, `404.html`, the self-unregistering `service-worker.js` and `.nojekyll`, linking to the profile hub. The deploy workflow publishes these files as-is; it never builds v2.

**Workflow** (`.github/workflows/pages.yml`, the only Pages workflow)
- Trigger: `push` to `main` or `dev`, plus `workflow_dispatch`. Pages source is "GitHub Actions" (the legacy `gh-pages` branch is no longer deployed; v2's `npm run deploy` is retired).
- The file is identical on `main` and `dev`: GitHub runs the copy on the pushed branch, so both branches must carry it.
- Every run builds **both** branches, whichever was pushed: it checks out `main` and `dev` into separate directories, builds each, and assembles one artifact with the `main` output at the root and the `dev` output in `dev/`. Then `actions/upload-pages-artifact` and `actions/deploy-pages` publish it. If either build fails, nothing is deployed and the previous deployment stays live.
- Build detection, per checkout:
  - if the root `package.json` exists and lists `astro` in `dependencies` or `devDependencies`, it is the Astro site: `npm ci && (npm run dupes || true) && npm run build` at the checkout root, output `dist/` (`npm run dupes` is the duplicate-media check, [section 2](2-content-model.md) "Duplicate media files": it prints duplicates, never fails the run and never writes);
  - otherwise, if the checkout root has an `index.html`, it is a static site: the checkout's files are published as-is, minus `.git/` and `.github/` (no install, no build);
  - otherwise the run fails.
- So until cutover `main` publishes the static maintenance page and `dev` builds Astro; after cutover both build Astro. Staging is only ever built from Astro: a `dev` checkout detected as static, or with neither case, fails the run. v2 is never built: a root `package.json` without `astro` (e.g. `react-scripts`) is ignored by detection.
- Deploy target is passed as one environment variable, `DEPLOY_TARGET` = `production` | `staging` (unset = `production`, so local builds behave as production). `astro.config` derives everything from it: `base` is `/` for production and `/dev/` for staging; `site` stays `https://gann4life.github.io`.
- Permissions: `contents: read`, `pages: write`, `id-token: write`. One concurrency group for all runs, no cancel-in-progress. No tokens, secrets or paid services; `GITHUB_TOKEN` is enough to read both branches of the same public repo.
- The `github-pages` environment must allow deployments from both `main` and `dev` (repo settings, deployment branch rules).

**Remote URL check** (`.github/workflows/remote-urls.yml` + `scripts/check-urls.mjs`)
- Purpose: report external URLs that stopped working. It only reports: it never edits content, never downloads media into the repo, never fails or blocks the Pages workflow (separate workflow, nothing depends on it).
- Triggers: `schedule` weekly (`cron: '0 6 * * 1'`, Monday 06:00 UTC), `workflow_dispatch`, and `push` to `dev` touching `src/data/profile.json` or `src/content/**`. GitHub runs scheduled workflows only from the default branch (`main`), so the schedule is active once the file is on `main`; like `pages.yml`, the file is identical on both branches. Concurrency group `remote-urls`, cancel in progress.
- What it checks: it checks out `dev` (always the superset of published content; CI has no drafts) and collects, with file and line: every `appearance` URL that is in effect (a `url` whose field has no `file`), profile `reel` and `links[].url` from `src/data/profile.json`; and every `http(s)://` URL in the frontmatter block of each published `work` and `blog` entry (`links`, `media` src, `credits` url, `upstream`), found by pattern inside the leading `---` block, published read as in "Drafts stay out of git" (no YAML library). Markdown bodies are not scanned. Duplicate URLs are requested once and listed with every place they occur.
- Request: Node built-in `fetch` (no dependency), `HEAD` with a 10 s timeout, redirects followed; on 403, 405, 501 or a network error it retries once with `GET` (body discarded). At most 4 requests at a time and 1 per host. Timeouts and 5xx are retried once after 30 s.
- Result per URL: **OK** = final status 2xx (for appearance URLs also a `content-type` starting with `image/`); **Broken** = 404, 410, other 4xx except below, 5xx after retry, DNS/TLS error, timeout, or an appearance URL that is not an image; **Unverified** = 401, 403, 429 (sites that block bots).
- Issue: exactly one issue titled `Broken remote URLs`, labels `type:bug`, `scope:content`, `priority:medium`, `status:ready`, found among open issues by that exact title. If any URL is Broken: create it, or replace its body if open. The body lists Broken, then Unverified, as a table (URL, status or error, field, `file:line`), plus the checked commit SHA and the run date. Unverified URLs alone never open the issue. If nothing is Broken: close the open issue, if any, with a comment naming the run. Labels that do not exist are skipped with a warning, never a failure. Uses `gh` from the runner.
- Permissions: `contents: read`, `issues: write`, nothing else; `GITHUB_TOKEN` only, no secrets, no third-party or paid service. This is the only CI job that writes to the remote, and only to that one issue.
- Exit code: 0 whatever the URLs return; non-zero only if the script itself crashes.
- The script exports its pure helpers (URL classification, collection from a given root, frontmatter block, host, draft test) for the tests; the run itself sits behind an entry-point guard, so importing the module does nothing.

**Tests** (`npm test` + `.github/workflows/test.yml`)
- `npm test` = `node --test --test-concurrency=1 "test/*.test.mjs"`: Node's built-in test runner, no test dependency. Files run one at a time because the build and dev smokes share `dist/` and `.astro/`.
- `test/build-smoke.test.mjs`: the staging build (`DEPLOY_TARGET=staging`) and the production build both exit 0; in the staging `dist/`, every root-absolute `href`/`src` in HTML starts with `/dev/` (the `dist/` half of the [section 3](3-pages.md) base-path check). After each build no text output in `dist/` contains `data-edit-` or `__editor` ("In-site editor"; the test also checks the older `data-editor` prefix, `work-editor` and `js-yaml`). Leaves `dist/` holding the production build.
- `test/dev-smoke.test.mjs`: skipped when `CI` is set (CI has no drafts). Reuses a dev server answering 200 on `localhost:4321` (fails if one answers anything else, e.g. a staging server), else starts `astro dev` and stops it afterwards. Expects 200 for the home, `/blog/` and every post, and every `/work/<slug>/` including drafts; then runs `npm run build` and expects 200 again for draft entries with a cover (regression for issue #77, [section 8](8-open-decisions.md) "Known issues").
- `test/exclude-drafts.test.mjs` and `test/dedupe-media.test.mjs` run the scripts as subprocesses inside a temporary directory (a git repo for exclude-drafts); they never touch the working repo. The `--hook` mode of `dedupe-media.mjs` is not covered. `test/check-urls.test.mjs` imports the helpers of `scripts/check-urls.mjs` and makes no network request. `test/vocab.test.mjs` fails when a work entry names a tool missing from `TOOLS` in `src/vocab.ts` (Keystatic's Tools picker would drop it on save). `test/editor.test.mjs` (unit tests with a stand-in schema; the symlink-escape case is skipped on Windows without symlink permission) imports the helpers of `integrations/editor/` and checks, on fixtures in a temporary directory: id → file resolution per collection (explicit `slug:`, bad ids, path escapes), request checks, per-type value checks and merge + validation (`422` cases, honesty refinements included), images (type sniffing, size limits, Keystatic-style target paths for image fields and list items, gallery reorder and removal moving files including swaps, no write when the target already holds the bytes, copying from `shared/`, body image naming and clash suffixes, rollback when a write fails, deletion only inside the entry's folder and only when unreferenced), the written bytes for fixtures saved by Keystatic, and that loading and re-dumping an unchanged Keystatic-written fixture gives identical bytes. `test/content-fields.test.mjs`: every registry field exists in the generated Keystatic collection and vice versa (body and slug aside), every `enum`/`tags` field has options, and every `refs` field names a registered collection. Neither touches `src/content/`.
- Workflow: `pull_request` to `dev` or `main`, `ubuntu-latest`, Node 22, `npm ci && npm test`. Permissions `contents: read` only; no secrets. Concurrency group per ref, cancel in progress. It does not deploy and `pages.yml` does not depend on it; making it a required check is a branch-protection setting, not part of this spec.
- Local verify step before committing: `npm test` (it includes both builds), plus frontmatter validation when content changed.

**In-site editor** (issue #136, redesigned 2026-10-30, [section 8](8-open-decisions.md); status: built, #152 to #156 (registry, generic endpoint, client, blog hooks, uploads); steps in [section 5](5-phases.md) "Phase 6")

The default way to edit content on the dev server: every field of a `work` entry or a `blog` post is edited on the item's own rendered page (edit mode, [section 3](3-pages.md)), images included. Keystatic stays installed as the alternative ("Edit in Keystatic" inside edit mode) and for what the editor does not do: creating entries and posts, changing a slug, and the Profile. Files keep Keystatic's format, so either tool opens what the other saved.

- **Exists only under `astro dev`, by construction**:
  - A local Astro integration, `integrations/editor/index.mjs` (renamed from `integrations/work-editor/`: it is no longer work-only), is added to `integrations` in `astro.config.mjs` only when `isDev` (as Keystatic is). Its `astro:config:setup` hook also returns early unless `command === 'dev'`.
  - `astro:config:setup` → `injectScript('page', …)` loading `integrations/editor/client.ts` (plain TypeScript and DOM, its own CSS file; no framework, no island, no new dependency). The script does nothing on pages without editor hooks.
  - `astro:config:setup` → `updateConfig({ vite: { plugins: [...] } })` adds a dev-only Vite plugin (`apply: 'serve'`) whose `configureServer` registers the middleware serving the endpoint below, then moves it to the front of the middleware stack so it runs before Vite's own CORS middleware ("Request checks"). No adapter, no `output: 'server'`, no Astro API route under `src/pages/`.
  - Page hooks come from one helper, `editHooks` in `src/lib/edit-hooks.ts`: `editHooks.entry(collection, id)` returns `{ 'data-edit-entry': '<collection>/<id>' }` and `editHooks.field(...names)` returns `{ 'data-edit-field': '<name> <name>…' }` in dev, and `{}` otherwise (`import.meta.env.DEV`, replaced with `false` in builds). Pages and components spread them on existing elements; there is no per-field wiring and no empty placeholder markup.
  - Guard test: after the production and the staging build, no file in `dist/` contains the strings `data-edit-` or `__editor` (`test/build-smoke.test.mjs`).
- **Module boundaries** (dependency direction `integrations/editor/` → `src/lib/` → `src/vocab.ts`, never the other way):
  - `src/vocab.ts`: value lists and their display labels (`KIND_LABELS`, `CONTEXT_LABELS`, `ROLE_LABELS`, `STATUS_LABELS` move here from `src/lib/work.ts`, which re-exports them, because the registry must load where `astro:content` does not exist: `keystatic.config.ts` and the dev middleware).
  - `src/lib/content-fields.ts`: the field registry (below). Imports only `src/vocab.ts`.
  - `src/lib/content-schema.ts`: `schemaFor(collection, image)`, the Zod object built from the registry. Imports only `astro/zod` and the registry. Replaces `src/lib/work-schema.ts` and the inline `blog` schema in `src/content.config.ts`.
  - `keystatic.config.ts`: builds each collection's `schema` from the registry with one local `toKeystatic(fields)` function; the Profile singleton stays hand-written.
  - `integrations/editor/`: loads the registry and `schemaFor` through `server.ssrLoadModule` (TypeScript and `astro/zod` resolve as in the site). `file.mjs` (kept from `work-editor`, generalised): request checks, collection + id → file, split, YAML read/write, date handling, per-type value checks, merge, hash, per-file lock, temp-file write. `assets.mjs` (new): upload decoding, type sniffing, naming, writes and deletions. Both are pure exported helpers with no side effects on import. The asset reference match is imported from `scripts/exclude-drafts.mjs`, which exports it behind an entry-point guard (as `scripts/check-urls.mjs` does), so the asset file rule has one implementation. Nothing under `src/` imports from `integrations/` or `scripts/`.
  - What `work-editor` keeps: request checks, id resolution, `splitEntry`, `js-yaml` read/`dump`, date-only values, hash + `409`, the per-file lock, the temp-file-then-rename write, the error model. What is replaced: `EDITABLE_FIELDS`, `DATE_FIELDS` and the per-field branches of `parseUpdate` (now per type, from the registry), the `work`-only URL prefix and folder, the per-field client code of #139, and the `data-editor-*` hooks.
- **YAML library**: `js-yaml` 4.x — the library Keystatic itself uses (`load` to read, `dump` with no options to write, in `@keystatic/core`). It is already installed as a Keystatic dependency; it becomes a direct dependency in `package.json` at the major version Keystatic resolves, so the editor does not rely on hoisting. `yaml` 2.x is also in `node_modules` (pulled in by the toolchain) and is not used: only `js-yaml` reproduces Keystatic's output.

**Field registry** (`src/lib/content-fields.ts`)
- `COLLECTIONS = { work, blog }`. Per collection: `fields` (ordered list, below), `dir` (`src/content/work`, `src/content/blog`), `assets` (`src/assets`, `src/assets/blog`; uploads go to `<assets>/<id>/`, written as `../../assets/<id>/…` or `../../assets/blog/<id>/…`), `reserved` slugs (work `c`, `t`, `site`, `all`, `blog`, `shared`, the last two because `src/assets/<slug>/` would collide with `src/assets/blog/` and `src/assets/shared/` (decision 2026-10-31); blog `page`; one list for Keystatic and the Zod schema), Keystatic `label` and `columns`, and `refine`, the collection's cross-field rules as a function (work: the honesty rules of [section 2](2-content-model.md), today's `superRefine`: ai-built roles and position, fork `upstream` and `credits`; blog: none).
- A field is plain data: `name`, `type`, `label`, `help` (tooltip in the editor, description in Keystatic; replaces `FIELD_HELP`), and as the type needs: `options` (`{ value, label }[]`, from `src/vocab.ts`), `collection` (target of `refs`), `fields` (item fields of a `list`), `required`, `default` (value when the key is absent), `initial` (Keystatic's value for a new entry), `itemLabel` (Keystatic only; dropped when sent to the editor).
- Types, one mapping each, used by `schemaFor`, `toKeystatic` and the editor client:

| `type` | In the file | Zod | Keystatic | Editor control |
|---|---|---|---|---|
| `text` | one-line string, trimmed | `string` (`min(1)` if required) | `fields.text` (`title`: `fields.slug` with `reserved`) | text input |
| `longtext` | string, LF, trimmed | `string` | `fields.text` multiline | auto-growing textarea |
| `markdown` | the body after the frontmatter (only `body`) | — | `fields.markdoc`, images in `<assets>/<id>/` (Keystatic keeps the given name; the editor's names differ, "Uploads") | auto-growing textarea of raw Markdown, plus "Insert image" |
| `boolean` | `true` / `false` | `boolean` | `fields.checkbox` | toggle |
| `enum` | one option value | `enum` | `fields.select` | select showing the option labels |
| `date` | `YYYY-MM-DD` | `coerce.date` | `fields.date` | date input |
| `url` | `https://…` | `url` (with `default: ''`: url or empty) | `fields.url` | URL input |
| `tags` | list of option values | `array(enum)` | `fields.multiselect` | compact multi-select (chips) |
| `refs` | list of entry ids of `collection` | `array(string)` | `fields.array(fields.relationship)` | compact multi-select of entry titles |
| `list` | list of objects with `fields` | `array(object)` | `fields.array(fields.object)` | repeated group: add, remove, move up / down |
| `image` | path relative to the entry file | `image()` (editor: `string`) | `fields.image` into `<assets>/<id>/`, named after the field ("Uploads") | thumbnail with Replace / Remove; Add when empty |

- `required` without `default` → required key; `default` → `.default(value)`; neither → `.optional()`. `slug` is not a registry field: `schemaFor` adds the optional `slug` with the `reserved` check, Keystatic edits it through the `title` slug field, the editor never edits it.
- Order = the page's reading order (user rule: the editor mirrors the page). It is the field order of the Keystatic form and of the editor's field panel.
  - `work`: `kind`, `context`, `started`, `ended` (when built, [section 2](2-content-model.md)), `status`, `team`, `draft`, `featured`, `title`, `position`, `authorship`, `media` (list: `type` enum, `src` text, `caption` text), `cover`, `contribution`, `roles` (tags), `body`, `origin`, `upstream`, `links` (list: `label` text, `type` enum, `url` url), `tools` (tags of `TOOLS`), `credits` (list: `name` text, `role` text, `url` url), `usedIn` (refs to `work`), `gallery` (list: `image` image, `caption` text).
  - `blog`: `date`, `pinned`, `featured`, `draft`, `title`, `summary`, `cover`, `body`, `work` (refs to `work`).
- Changes the schema makes visible, none affecting existing entries: `tools` is checked against `TOOLS` by the schema (today only by `test/vocab.test.mjs`, which every entry passes); the work slug `all` is reserved in the schema as well (no entry uses it).
- Adding a field or a collection is a registry change plus rendering it on the page with a `data-edit-field` hook; no editor code changes.
- **Not editable in the site**: `slug` only. Renaming moves the entry file and its asset folder, changes the URL, and leaves `usedIn` / `work` references in other files pointing at the old id; that stays in Keystatic, reached through "Edit in Keystatic". Changing the title never changes the slug.

**Endpoint** (served by the middleware; `<base>` is Vite's `base`, `/` or `/dev/`)
- `GET <base>__editor/<collection>/<id>` → `200 { id, hash, values, body, form }`: `values` the raw frontmatter value of every registry field present in the file (dates as `YYYY-MM-DD`), `body` the Markdown after the frontmatter, `hash` the SHA-256 (hex) of the file bytes as read, `form` the collection's registry as JSON, with the options of each `refs` field filled in from the target collection's files (`{ value: id, label: title }`, drafts marked, the entry itself left out).
- `PUT <base>__editor/<collection>/<id>` with `{ hash, set, body?, uploads? }` → `200 { hash }` (hash of the written file). `set` may hold any registry field; a field set to `null` is removed from the file. Cleared fields are written as a Keystatic save writes them (measured in #152, implemented): the client sends `null` (key removed) for an emptied optional `text`, `url` or `image` (the editor treats `longtext` and `date` the same way; inside a `list` item an empty optional `text`, `url` or `longtext` sub-field is left out), `[]` for an emptied `list`, `tags` or `refs`, and `false` for an unchecked non-required `boolean`. `uploads` is `[{ token, name, data }]` (below).
- Value checks per type before merging (`400` on failure): `text` string, trimmed, non-empty when required; `longtext` string, LF, trimmed; `boolean`; `enum` and `tags` values among the options; `date` a real `YYYY-MM-DD`; `url` a string; `refs` ids matching the id pattern; `list` an array of objects holding only the item's fields, each checked by its type; `image` a path the entry already referenced before this save (kept or moved) or `{ "upload": "<token>" }`; `body` a string.
- Errors, JSON `{ error }` (plus `issues` on 422), nothing written: `400` malformed JSON, unknown field, wrong value, unknown upload token, an image path the entry did not reference; `403` failed request check; `404` unknown collection or no entry with that id; `409` `hash` differs from the file on disk (saved elsewhere, e.g. in Keystatic, since the page loaded); `413` request over 64 MB or an upload over 10 MB; `415` an upload that is not PNG, JPEG, WebP, AVIF or GIF; `422` the merged entry fails `schemaFor(collection)` (`issues: [{ path, message }]`, honesty refinements included) or the file has no leading `---` block; `500` read/write failure.

**Uploads** (images for `image` fields, `list` items with an image, and the body)
- Sent inside the `PUT`, base64 in `uploads`, so a save stays one `application/json` request (the same-origin checks below hold) and nothing reaches the disk before the whole save is validated. `token` matches `^[a-z0-9]{1,16}$`. In `set`, an image value `{ "upload": "<token>" }` uses it; in `body`, `](upload:<token>)` marks an image inserted by "Insert image" and is replaced by the final relative path.
- Accepted: PNG, JPEG, WebP, AVIF, GIF, recognised by their first bytes (the given name's extension is ignored). SVG is not accepted. At most 10 MB per decoded file and 64 MB per request.
- **Keystatic's layout is the rule** (decision 2026-10-30 "Editor images use Keystatic's names", [section 8](8-open-decisions.md)): the editor writes image files where and under the names a Keystatic save would, so a save in either tool leaves the other nothing to rename. Measured: Keystatic names a frontmatter image after its field, and on every save moves any image an image field references to that name (deleting the old file and repointing the frontmatter).
- **Image fields** (frontmatter), relative to the entry's folder `<assets>/<id>/` (`src/assets/<id>/` for work, `src/assets/blog/<id>/` for posts; created if missing):
  - top-level `image` field `<field>` → `<field>.<ext>` (e.g. `src/assets/<id>/cover.png`, written as `../../assets/<id>/cover.png`);
  - `image` sub-field `<sub>` of item `<i>` (0-based, current position) of `list` field `<field>` → `<field>/<i>/<sub>.<ext>` (e.g. `src/assets/<id>/gallery/2/image.jpg`). Today `gallery.image` is the only one; `media.src` is a `text` field (a URL or a `/media/` path, [section 4](4-media.md)), never an upload.
  - `ext`: for an upload, from the detected type (`png`, `jpg`, `webp`, `avif`, `gif`); for an existing file, its current extension unchanged.
- **Every save normalises every image field**, as Keystatic does: after the merge, each image value gets its target path above. A value whose file is already there is left alone; otherwise the bytes (upload, or the file it pointed to, wherever it is, `src/assets/shared/` included) are written to the target. So reordering gallery items moves their files to the new indexes, removing an item moves the ones after it down, replacing an image overwrites its target, and the first editor save of an entry with older, hand-chosen names renames them, exactly as its next Keystatic save would.
- **Body images** (Markdown, "Insert image"): folder `<assets>/<id>/`; name = the given name without its extension put through the tool slug rule ([section 2](2-content-model.md) "Tool pages"), cut to 40 characters (`image` if empty), plus `ext` from the detected type; if that name is taken by different bytes or is a target of an image field above, `-2`, `-3`, … is appended to the stem. A body upload never takes the stem of one of the entry's image fields (`cover`, `gallery`), whatever its extension. Only Markdown image links `![…](…)` in the body count as body image references (for clashes and deletion). Existing body image links are never rewritten. This deliberately differs from Keystatic (measured below; decision 2026-10-31, [section 8](8-open-decisions.md)).
- **Order of a save with images**: check and plan everything first, including the schema on the merged entry with the final paths, and read every source file into memory. Then write each target whose bytes change (temp file + rename, as entries; overwriting is allowed only on the targets of image fields, which belong to the entry), write the entry, then delete. If any write fails, every target this request overwrote gets its previous bytes back, every file it created is removed, and the entry file is left as it was (`500`).
- **Replaced and removed images**: after the entry is written, each image path it referenced before the save (image fields, list items, body image links) and no longer references is deleted when the file sits inside the entry's own folder and no other file under `src/` or `keystatic.config.ts` references it (the asset file rule's text match, [section 2](2-content-model.md)); a folder this leaves empty inside the entry's folder (e.g. `gallery/3/`) is removed. Files outside the entry's folder, e.g. `src/assets/shared/` after a duplicate merge, are never deleted; one left unreferenced gets the exclude script's usual `WARNING`.
- **Drafts and duplicates**: no new rule. An image saved to a draft lands in its slug folder and stays local under the asset file rule; an image saved to a post lands in `src/assets/blog/<id>/` and is judged by explicit reference. Each entry keeps its own copy of a shared image, as with Keystatic: byte-identical files in different entries are reported by the duplicate resolver, and a manual merge into `shared/` of a file an image field references lasts only until that entry's next save in either tool ([section 2](2-content-model.md) "Duplicate media files").
- **Measured 2026-10-30 (#156)** and the resulting rules (decision 2026-10-31, [section 8](8-open-decisions.md)):
  - Body images: Keystatic keeps the given name verbatim (spaces, case; the link is URL-encoded) and silently overwrites on a clash, losing the earlier image. The editor deliberately differs and keeps the slugged name with `-2`, `-3` on a clash: Keystatic reads either and never renames, moves or deletes body images on later saves, so the safer rule costs nothing.
  - Extension: Keystatic takes it from the given file name, case kept (`a.JPEG` → `cover.JPEG`), and keeps an existing file's extension when it moves it. The editor's extension from the detected type is stable under a later Keystatic save, so the rule stands.
  - Image fields outside `<assets>/<id>/` (e.g. `shared/`): Keystatic cannot read them; the field shows empty and its next save drops the key without copying the file. The editor copies such an image into the entry's folder on save (rule above). Image fields should never point at `shared/`; the duplicate resolver stays report-only for entry-owned images. A body image outside `<id>/` shows as "Missing image" in Keystatic.
  - Unreferenced files in the entry folder and `shared/` copies are not deleted by a Keystatic save. Emptied `gallery/<i>/` folders are left behind by Keystatic; the editor removes them.
- Alt text: unchanged rules. A gallery item's `caption` is its alt text and caption, as on the page; the cover stays decorative (`alt=""`); "Insert image" asks for the alt text and writes `![<alt>](…)`.

**Request checks** (all requests; any failure → `403`, nothing read or written)
- Remote address is loopback: `127.0.0.1`, `::1` or `::ffff:127.0.0.1`. So `astro dev --host` on a LAN still refuses other machines.
- `Host` header hostname is `localhost`, `127.0.0.1` or `[::1]` (blocks DNS rebinding).
- `PUT` only: `Origin` present and equal to `http://<Host>`; `Content-Type` is `application/json` (cross-origin pages cannot send it without a preflight, and the middleware never answers preflights or sets CORS headers; it sits ahead of Vite's own CORS middleware, which would otherwise answer both for any localhost origin); `Sec-Fetch-Site`, when sent, is `same-origin`.
- No other methods: `405`.

**Files touched**
- `<collection>` must be a key of `COLLECTIONS`; `<id>` must match `^[a-z0-9]+(?:-[a-z0-9]+)*$`. The file is found among the top-level `*.md` files of the collection's `dir` by the id rule of the glob loader: explicit top-level `slug:` (read as in [section 2](2-content-model.md) "Frontmatter parsing"), else the file name without `.md`. Nested folders are not supported (`404`). The resolved real path (symlinks followed) must sit inside that `dir`; anything else is `404`.
- Entries: the editor only edits existing ones; it never creates, renames or deletes an entry file. Changing the title does not change the slug or the file name.
- Images: written only inside the entry's own asset folder (`<assets>/<id>/`, its real path confined like entries), under the path rules above; a file with different bytes is overwritten only when it is the target of one of the entry's image fields; files and emptied folders are deleted only under the rule above. Reading a source image may happen anywhere under `src/assets/` (e.g. `shared/`); paths that resolve outside it are `400`. No other file is created or deleted.
- Write: to a temporary file `.<file name>.<random UUID>.editor-tmp` in the same folder, created exclusively (`wx`, so an existing file or symlink at that name is never followed) (no `.md` ending, so the content loader and the exclude script ignore it; `.gitignore` lists `*.editor-tmp`), then renamed over the target. No shell, no `child_process`, no `eval`, no dynamic import of request data.

**File format** (what a save writes)
- The file is split at the leading `---` block ([section 2](2-content-model.md) "Frontmatter parsing" boundaries; CRLF accepted on read). The frontmatter is read with `js-yaml` `load` (default schema, as Keystatic), the keys in `set` are replaced in place (a key not yet present is appended at the end; `null` removes the key), and the whole entry is validated with `schemaFor(collection, () => z.string())` before anything is written.
- Written as `---\n` + `dump(data)` + `---\n` + body, with `js-yaml` `dump` and no options — the same call Keystatic makes — so key order is the file's own and scalars, quoting and folded `>` / `>-` strings come out as Keystatic writes them. Values of every `date` field are written as plain `YYYY-MM-DD`, as Keystatic's date field does (a `Date` whose `toISOString` returns the date string).
- Emptied fields, as a Keystatic save writes them (measured in #152, implemented): the key is removed for `text`, `url` and `image` (also `longtext` and `date` in the editor); `[]` is written for `list`, `tags` and `refs`; `false` for a non-required `boolean`. Booleans are always written.
- Body: written as received, line endings normalised to LF; a non-empty body that does not end with a newline gets one. Body Markdown is never reformatted by the editor.
- Untouched keys keep their values, but a file last written by an import script (flow lists like `roles: [artist]`, double quotes) is normalised to Keystatic's style on its first editor save, exactly as a Keystatic save would; that diff is formatting only. Keystatic writes keys in registry order, so the first Keystatic save of an entry written before the registry (or by the editor, which keeps the file's key order) also reorders its keys once; values are unchanged (accepted 2026-10-30, #152).

**Staging is never indexed**
- Every staging page carries `<meta name="robots" content="noindex, nofollow">`; production pages do not.
- The staging build emits no `sitemap.xml` and no `robots.txt` and does not link a sitemap from `<head>`. Crawlers read `robots.txt` only at the host root, so the production `robots.txt` is the only one that matters; it does not `Disallow: /dev/` (a disallowed page cannot be crawled, so its `noindex` would never be seen). The production sitemap never lists `/dev/` URLs.
- GitHub Pages serves only the root `404.html`, so a missing page under `/dev/` shows the production 404.

**Retired v2 service worker**
- Older v2 builds registered a service worker at `/service-worker.js` (scope `/`). Browsers that still hold it re-fetch that URL on navigation and keep it unless the new script removes itself, so the production root must always serve a self-unregistering `/service-worker.js`.
- v3 ships it as `public/service-worker.js`, a plain static file (no build step, no dependency, not a module). Behaviour: on `install`, `skipWaiting()`; on `activate`, delete only the caches v2 created (names starting with `workbox-` or `sw-precache-`, the prefixes CRA's Workbox and older sw-precache workers use; to verify against the deployed v2 worker), call `self.registration.unregister()`, then `navigate()` each window client to its current URL so the page reloads without the worker. It has no `fetch` handler.
- v3 pages never register a service worker (no `navigator.serviceWorker.register` anywhere in `src/`).
- Production: the file lands at `/service-worker.js`, the URL v2 registered. Before cutover the maintenance page on `main` carries its own copy with the same behaviour.
- Staging: the same file lands at `/dev/service-worker.js`. v2 never registered a worker there, so it is inert and kept only so both builds come from one `public/`; it adds no indexing or routing concern.
- It must never delete every Cache Storage entry of the origin: other repos publish under `gann4life.github.io` and share its storage.
- Removal: only when a later decision states that v2 workers are no longer expected in the wild; not before.

**Base path**
- The site must work under any `base`. Internal links and asset URLs follow the base-path rule in [section 3](3-pages.md).
